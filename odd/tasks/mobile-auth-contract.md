# Feature: mobile auth contract

Spec: https://github.com/ChordanDev/myfood-monorepo/issues/1 (label `ready-for-agent`).
Tickets (sub-issues of #1, native blocking edges): #6 prefactor envelope+TTL (= T1), #7 login + CurrentMe (= T3 + login half of T4), #8 signup (= signup half of T4), #9 device sessions (= T2), #10 contract closure (= T5). Work one ticket per session; #7 is the frontier after #6.
Branch: `feat/mobile-auth-contract` (from `main` at `38a4a7e`).

## Objective

`apps/api` serves the auth contract `apps/mobile` already implements, so a person can sign up, log in, refresh, log out and be routed by `GET /api/me` end to end against the real backend.

## Problem

Mobile calls `POST /api/auth/{signup,login}/{request-code,verify-code}`, `/api/auth/refresh`, `/api/auth/logout` and `GET /api/me` with camelCase bodies and reads `{ error: { code, message } }`. The API exposes `/api/auth/email-code/*`, snake_case, flat error strings, a three-shape verify response, non-rotating refresh tokens, a no-op logout and no Trial on fresh Accounts.

## Scope and constraints

- Mobile contract wins; mobile code does not change except un-skipping its contract test.
- Legacy routes stay. Mobile is the only client, so `/api/auth/refresh`, `/api/auth/logout`, `GET /api/me` and the auth plugs change behaviour in place.
- Trial is 7 days (code wins over old PRDs).
- Decisions taken (see spec): membership resolution owner-first, `account_not_found` when no active Membership, email existence revealed on request-code, access TTL 1h, refresh TTL 30d, resend cooldown 60s, plan mapping `trial/individual → individual`, `family_4 → family`, `family_6 → family_plus`.
- RDD is on (global). Review candidate = each work-unit commit; assess after each commit with `--base-ref <last reviewed boundary> --committed-only`.

Migration + schema `device_sessions` (named after the glossary term, not the earlier `refresh_sessions`): one row per refresh token with `token_hash` (SHA-256 hex, unique), `user_id`, `membership_id` (the Account scope), `device_id`, `expires_at`, `revoked_at`, `replaced_by_id` (self reference). New service `DeviceSessions` (`open`, `rotate`, `revoke`, `sweep`); the mobile verify routes open a session instead of calling `mint_token_pair/2`, which stays as is for the legacy callers. `POST /api/auth/refresh` takes `{ refreshToken }`, rotates and answers `{ accessToken, refreshToken, tokenType }`; `POST /api/auth/logout` takes `{ refreshToken }`, revokes and answers 204. Decisions (technical defaults, taken 2026-10-07): the refresh JWT carries the row id in a `sid` claim and the row is found by token hash; all five `refresh_token_*` codes answer 401 (mobile branches on the code only); a missing, malformed, wrongly typed or unsigned token and a token without a row answer `refresh_token_invalid`, so refresh tokens minted by the legacy routes stop being refreshable (the spec replaces that behaviour, the old clients are not in use); check order is replayed (`replaced_by_id` set) → revoked → expired (JWT `exp` or row `expires_at`) → session mismatch (JWT `sub` or `sid` differs from the row); a replay revokes every active row of that User and `deviceId`; rotation locks the row, so a concurrent second refresh is a replay, with no grace window; the new row inherits `device_id` and `membership_id`, and access claims are rebuilt from the current Membership (not active → `account_not_found`, like login); opening a session for a User and `deviceId` that already has active rows revokes them (one Device session per phone); logout has no auth plug, ignores the `Authorization` header and answers 204 for unknown, revoked or missing tokens; `deviceId` is capped at 255 characters under the existing `code_invalid` rule; `sweep` deletes rows past `expires_at` and rows revoked more than 7 days ago (kept that long so a replay is still recognised) and ships as a function only, since ADR 0002 assigns the schedule to Oban, which is not installed. Route: delegated writer (2+ non-trivial files; mapping by one read-only explorer). - [x] T2-h — Device session hardening (ticket #9, from the Jorge el Curioso review of PR #56, findings CORR-DATA-02, CORR-DATA-03 and CORR-DATA-01, verified against the code). (1) A `deviceId` with a NUL character, or one within 255 graphemes but wider than the column, passes validation and fails on insert, a 500 after the code was consumed: the rule moves to one place owned by `DeviceSessions` (valid UTF-8, not blank, no NUL, at most 255 bytes), the controller asks it before the code is touched and still answers `code_invalid`, the changeset and the column state the same limit. (2) One active Device session per User and `deviceId` is not enforced under concurrency: a login racing an in-flight refresh of the same phone can leave two active rows. `open` and `rotate` serialize on a transaction-scoped advisory lock keyed by User and `deviceId`, taken before any row lock (rotation reads its row first to learn the key, then locks and re-reads it), and a partial unique index on `(user_id, device_id) WHERE revoked_at IS NULL` replaces the plain one as the backstop; rotation revokes the old row before inserting its successor so the index holds inside the transaction. The index alone was rejected: it would turn the race into a 500 after the code was consumed. The migration is edited in place (not merged or deployed yet). (3) `User` and `AccountMembership` gain `@type t`, which the new spec and older ones already referenced. Not taken: finding CORR-DATA-05 (legacy password and social refresh tokens) stays as decided in the spec, mobile calls neither route, and it belongs to ticket #14; the grace window for a retried refresh becomes its own issue. Route: delegated writer (2+ non-trivial files). Test-first.
